# Codex Desktop 26.1117.4957 ChatGPT 模式“工作”新聊天换成 ChatGPT Work 输入框

Windows 商店版 Codex Desktop `26.1117.4957` 上，ChatGPT 模式 →“工作”标签的新聊天（首页与项目内“开启新聊天”）不再渲染 Codex composer，而是 ChatGPT 自己的 Work composer。Agent 选择器不出现，Hub 自动验收的三项都以 `picker` 失败。同一台机器上切到 Codex 模式后，现有集成完整可用。

## 现场结论

- 新输入框是 `form[data-thread-find-composer][data-composer-placement=home|thread]`，内部没有 `[data-codex-composer-root]`。已提交 React 树中：`isWork: true`、`conversationOrigin: "tpp"`、`conversationId: "local-chatgpt:<uuid>"`、`defaultTppLocalExecutionSelected: true`；首页的 `runLocationState` 为 `{ effectiveLocation: "cloud", canChooseLocation: false }`。
- 发送一条测试消息后，Codex 的 `~/.codex/sessions` 下没有新增 rollout，侧栏数据把它列为 ChatGPT 服务器会话（`conversation_origin: "tpp"`，归属 ChatGPT 项目 `g-p-…`）。也就是说，这类会话由 ChatGPT 后台（`work.cloud-orchestration`）编排，只有工具在本机经 `codex exec-server --remote` 执行，不存在可交给外部 Harness 的 app-server Thread。
- 因此只补识别规则不够：给新输入框补标记后，Agent 按钮能挂上，但 ownership 检查失败（“无法确认会话的 Agent”）。Host 无法、也不应拦截这条提交。
- 旧版本（26.1106、26.1117.31558）的包里也有同一套 ChatGPT Work 代码，是否启用由服务端开关决定。

## 处理方式（降级入口）

`renderer-chatgpt-work-bridge.ts` 只识别上述 ChatGPT Work composer（`isWork: true` 且 `conversationOrigin: "tpp"`，且不含 Codex composer 根），在发送按钮左侧放一个与 Agent 选择器同尺寸的按钮（`aria-label` 为 `Select Agent, current ChatGPT Work`）。菜单说明这类对话在 OpenAI 云端运行、Hub 接管不了，列出 Codex 与已就绪的外部 Agent。选择后：

1. 写入新对话 Agent 偏好（与 Codex composer 的新草稿默认 Agent 是同一份）；
2. 通过 Codex 模式切换组件已发布的 `onModeSelect("codex")` 切到 Codex 模式；
3. 在同一个侧栏项目行（`data-app-action-sidebar-project-id` 与 Work composer 的 `projectId` 相同）点它的新聊天；没有项目时点 Codex 的“新聊天”。

新草稿由原有 Composer 集成接管，Agent 已预选。找不到模式开关或新聊天按钮时，菜单里给出手动操作提示（偏好已写入）。桥接从不拦截 ChatGPT Work 的提交，ChatGPT“聊天”标签的普通输入框不挂载。

## 依赖与复核点

- 私有标记：`isWork`、`conversationOrigin`、`projectId` props，模式组件的 `mode` / `onModeSelect` / `codexAvailable` props，侧栏 `data-app-action-sidebar-project-id`。Desktop 更新后需在真机重新探测。
- 验证：Windows 4957 真机，从 ChatGPT 模式“工作”新聊天开始跑 `tools/selfheal/ui_check.mjs` 三项全部通过；单元测试 `packages/renderer-extension/test/renderer-chatgpt-work-bridge.test.ts`。
